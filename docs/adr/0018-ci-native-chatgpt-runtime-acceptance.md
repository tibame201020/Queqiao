# ADR-0018 — CI-native ChatGPT on-demand Queqiao acceptance

- Status: Accepted for the **acceptance definition**, implementation/live execution: **NOT ACCEPTED** (2026-10-15)
- Tracking: [#185](https://github.com/tibame201020/Queqiao/issues/185)
- Review base: source `main` `97cdc09b66c5894020b7fb6b1c08eccd0192ca1b`
- ADR-0017 and Issue #124 remain true for their **narrower interactive delegated publishing** POC, and cannot grant this architecture gate a PASS.

## Product goal, not a publication goal

An authenticated **CI ChatGPT session**, with its native custom-MCP connection/client within the CI Browser Harness, requests a bounded public Queqiao Agent tool through one registered **stable URL**. The fixed front door accepts the native tool request, provisions an **on-demand Lease** (new dynamic Queqiao Gateway/Worker behind the front door), sends the request to the ready runtime and returns its result to that **same ChatGPT conversation**. A Gateway original event and independently observed ChatGPT native tool-call/result, Worker output and disposal prove the sequence. Two independent reviewed-main runs must reuse exactly the same externally observed URL while using fresh CI sessions, original invocations, Gateway/Worker runtimes and disposed leases. A separate Controller Node.js test client is never the CI ChatGPT client for this purpose.

## Current facts / why the previous PASS cannot be promoted

- `.github/workflows/runtime-provider-browser-controller.yml` creates a run-specific `trycloudflare.com` quick tunnel and sets `gateway.publicBaseUrl` to it. A random tunnel hostname is **not** a stable URL.
- The Gateway/Worker is provisioned before the Worker ChatGPT synthetic prompt; the preflight is from workflow inputs, not ChatGPT demand.
- `apps/gateway/src/poc-gate3-worker-client.ts` (Controller Runner) calls MCP directly via the Node SDK, using the local `127.0.0.1` URL and a separate test OAuth client. This is a valid Gateway call, but not ChatGPT's original tool request.
- `packages/browser-harness-runtime/src/session-acceptance.ts` runs inside the ephemeral Worker Runner and `gate3-prompt.ts` produces plain synthetic TDD JSON. It does not independently observe a native Queqiao custom MCP tool-call event/response in that ChatGPT session.
- The later signal-notes Draft PR #4 and target CI are genuine, but GitHub App writes occurred in a different, external ChatGPT session. Content/hash agreement does not establish native CI tool-call origin. All previous Run IDs and stage-local receipts remain untouched.

## Trusted boundaries and stop rules

1. **Front door:** confirm an owned domain / installed named tunnel (or equivalent stable ingress) and its current authorized external DNS/credential model. A stable adapter MUST reject ephemeral quick tunnels. A fixed address alone is not live evidence: independently initialize MCP and list tools against it for **two independent reviewed-main runs**. If a permanent front door is needed to awaken a fully stopped Gateway, identify its actual owner, dispatch authority and fail-closed unbound route rather than asserting a nonexistent server. No DNS, credential or production publication changes are authorized by this ADR.
2. **Native origin:** confirm the real product supports a **registered ChatGPT custom MCP** accessible in the restored CI session and an original UI observation showing the model's native tool-call and response. A synthetic prompt instructing it to use the tool does not itself prove the tool existed or was called. A `Client.callTool` issued by a Controller test script is a negative control. The specific App name, tool semantics and permissions must be inspected before designing the probe; no fabricated DOM attribute, network interception, session cookie export or identity bypass.
3. **On-demand causal order:** CI-native tool intent → original Gateway receive → dispatch Lease → ready Worker → actual Worker result → Gateway return → same CI ChatGPT response → disposed Lease. Original Gateway audit must independently bind invocation/session and request/result digests, not just content SHA. Two runs: same fixed MCP URL, distinct CI session, invocation, Worker/Lease and controller Run IDs. An expired route, stale lease, ambiguous or missing original evidence fails closed.
4. **Independent verifier:** `assessCiNativeAgentRuns()` is only a strict **data-candidate** seam and always returns `NOT_VERIFIED`: even a passing two-run fixture yields `eligible_for_independent_provider_readback`, not PASS. The authoritative integration checker must **fetch** original provider evidence itself before issuing a completion receipt. Unit mocks or workflow description never satisfy the hosted gate. G3.4 publication checks are downstream optional, not an alternate proof.

### Review criteria

Standards: tests at the pure public candidate boundary; no private profile/session/secret data in repo/logs; strict status semantics; preserve existing CI checks and historical original audit data. Spec: prove the *model-originated* native request with fixed URL and demand-time runtime, not another content-to-GitHub handoff. Any eventual credential/DNS/production transition requires fresh exact owner approval.

## Slice B read-only product discovery (2026-10-15; no architecture PASS)

The current ChatGPT custom MCP product model uses an account-installed plugin and an externally reachable HTTPS MCP endpoint or supported Secure MCP Tunnel. The installed app must first appear as an actual candidate in the restored **CI ChatGPT** interface; an account/Controller-side app reference alone does not establish that visibility. On demand, a manually gated `native_mcp_preflight` mode in `browser-harness-gate3.yml` restores the existing session, types `@Queqiao` **without sending a message**, and only looks for one visible native app option/menuitem (or exactly one newly appeared differentiated button). This records a sanitized original CI run/attempt with `candidate=visible|not_observed`, but intentionally records `connectedMcp=false`, `nativeToolCallObserved=false`, `gatePassed=false` in every case. It does not click the app, launch a Worker, read the user's chats or record the UI. Negative cases fail closed. Real observed tool-call and independent Gateway events remain an entirely separate later acceptance gate.

A Cloudflare Quick Tunnel creates a random `trycloudflare.com` hostname, while a stable named Tunnel's public hostname requires an authorized domain and tunnel ownership. The Queqiao workflow currently only configures a Quick Tunnel. The existing GitHub Actions Secrets metadata contains no recognizably named ingress/tunnel URL/credential (name-only read, no values). No verified existing public Render service was found via its read-only service listing; this does not prove no infrastructure exists in other accounts. **Do not fabricate a stable host or install a new Cloudflare credential.** Hosted fixed-front-door implementation and ChatGPT app registration must follow verified operator-owned infrastructure and exact authorization. Product references: https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt and https://developers.cloudflare.com/tunnel/get-started/.

## Existing operator-owned Cloudflare Named Tunnel: original Hosted transport evidence (2026-10-15)

A previously created **Private POC repository** actually owns and can run a Named Tunnel using its already configured `CLOUDFLARE_TUNNEL_TOKEN`, `QUEQIAO_APPROVAL_SECRET`, `QUEQIAO_JWT_SIGNING_SECRET` and non-secret `QUEQIAO_PUBLIC_URL` variable. Public hostname is represented only by the existing private repository variable; no personal domain, session material or token is copied into this public repository. The main Queqiao repo's absence of Cloudflare secrets was not evidence that the existing private repo lacked authorization. The CLI-only operator check found no local Cloudflare account-wide certificate; this is immaterial because the private CI already has the *tunnel-specific run token*. Cloudflare specifies that a remotely-managed Tunnel runner can operate with its tunnel token, which does not itself grant general DNS/Worker-management rights. No new domain, DNS change, Cloudflare login or token replication was required.

The external public URL resolves and has valid TLS. Baseline private [Run `38688427345`] passed in GitHub Actions on its actual existing Named Tunnel: externally observed `/health` HTTP 200, unauthenticated `/mcp` HTTP 401 and TLS verify 0 while running; after cleanup, same fixed hostname returned HTTP 530. This proves fixed-DNS + ephemeral connector transport, **not** permanent live ingress.

TDD in that Private POC introduced the strict transport gate (PR #1, source `52d4536e2e2ed7f9c1d9f8007f552b352e188d7b`): exact healthy `/health=200`, unauthenticated `/mcp=401`, verified TLS, reject arbitrary reachable HTTP and quick-tunnel URLs. The first reviewed-main Hosted Run `38688836254` **FAILED** at the pre-enrollment `/health=200` wait. Original external evidence at that stage: worker-dependent `/health=503` while protected `/mcp=401`; Worker enrollment was skipped; cleanup succeeded. Root cause: circular readiness ordering, not a need to weaken the final health standard. TDD RED?GREEN fixed order in Private POC PR #2 (merged source `57a750e4267ce1380ff6f89be88bbd8d6c082b2b`): **pre-enrollment** require protected `/mcp` HTTP 401, then enroll the Worker and prove membership; **post-enrollment** require strict `/health` HTTP 200, `/mcp` HTTP 401 and TLS.

Second reviewed-main [Hosted Run `38689173302`] is original **SUCCESS**, with original connected GitHub App reread confirming every material job step: unit tests, existing Secret presence, cloudflared start, public ingress wait, Worker enrollment, runtime acceptance, `Verify Named Tunnel MCP transport`, bounded TTL, and `Cleanup` all `success`. Its same public URL externally returned HTTP 200/401 with valid TLS during the run, then HTTP 530 after job completion. These observations are a **Named Tunnel transport: VERIFIED** sub-gate; they are **not a model-native MCP invocation** and do not supersede previous `@Queqiao` candidate-not-observed evidence.

**Unresolved architectural prerequisite:** while Actions is offline the Name/DNS remains fixed but no `cloudflared` connector receives requests (observed 530). A **persistent ingress/dispatch control plane** with independently verified limited GitHub Actions dispatch authority is needed for a ChatGPT-originated request to wake a fresh CI runtime; the existing tunnel run-token alone cannot supply this control plane. Also verify the actually available/installed CI ChatGPT custom MCP connection and its registered display name. No such live control plane, model-native invocation or two-run on-demand proof has yet been established. Therefore #185 remains **NOT ACCEPTED**. Do not create or reuse a broad Cloudflare management certificate, put an Actions token into public files, treat /health as MCP initialize, or label the transport sub-gate as a full architecture PASS.
